# S1 CNN Anomalous Performance — Investigation Report

**Date:** 2026-07-26
**Scope:** Local-only investigation (repo history, code inspection, and the public HTTP mirror at
`et-vd.ijclab.in2p3.fr/~lorenzo-mobilia/EasyResNetPaper-v1/`). No cluster/SSH access was used —
all data below was pulled over HTTP or read from this local git clone.

**Trigger:** The CNN scores ~99.7% accuracy on `S1/results_15k_more_fainter`, a population injected
at 100,000–200,000 Mpc with optimal SNR ~1e-5. At that SNR the injected signal is many orders of
magnitude below the noise floor — no legitimate matched-filter or CNN-based statistic can detect it.
Any non-trivial accuracy on this population is definitive evidence of a bug, not a genuine detection
capability. This document lists every test run so far and ranks the candidate bug sources.

## 2. Tests performed and results

### 2.1 Image format / dimensions (all pools)
- All three raw image pools (`more-fainter/inj`, `fainter`, `Simulation-1-GN-images`) are
  512×256, 8-bit grayscale PNG, non-interlaced. No dimension/format discrepancy anywhere.
- `Simulation-1-GN-images` additionally contains two 2520×2520, 16-bit outlier files
  (`out-0.png`, `out-1.png`) that are unrelated composite/diagnostic images, not part of the
  per-event dataset.
- `S1/fainter/images/TT_map_SNR_10483.png` is a genuine **0-byte file on the server**
  (`Content-Length: 0`), a data-quality defect independent of the leakage question.

### 2.2 Embedded PNG metadata schema
Checked via `exiftool` across full/large samples of each pool (60/38/81 files):
- Shared fields: `Job_id, Activator, Distance, M1, M2, Merge_time, Optimal_snr, Seed, F_0, Q_factor,
  Amplitude, Phase, Time_jitter, Detector, Max_snr`.
- `S1/more-fainter` and `S1/fainter` additionally carry `S1z, S2z, Max_rwsnr, Chisq` in **100%** of
  sampled files; `Simulation-1-GN-images` has **0%** of these. Tag *emission order* also differs
  (`Max_snr` appears right after `Job_id` in GN vs. after `Detector` in the S1/ tree).
  Conclusion: `S1/` tree and `Simulation-1-GN-images` were generated by two different versions of
  the injection/imaging script.

### 2.3 Physical parameter distributions (raw image pools)
| Pool | Distance [Mpc] | Optimal SNR | Max SNR |
|---|---|---|---|
| more-fainter (n=60) | 2290–9890, mean 7430 | 0.40–2.09, mean 0.70 | 5.42–6.48, mean 5.89 |
| fainter (n=81) | 129–998, mean 720 | 3.57–35.4, mean 7.66 (median 6.63) | 5.50–31.0, mean 7.83 (median 6.63) |
| GN (n=38) | 204–997, mean 758 | 3.74–19.3, mean 6.47 (median 5.65) | 5.32–19.1, mean 7.23 (median 6.00) |

Findings:
- `more-fainter` is genuinely ~10x farther / much lower SNR than GN.
- `fainter`, despite its name, is **not** systematically fainter than GN — median/percentile SNR is
  close to GN's, with one outlier (`TT_map_SNR_10206.png`, distance 128.7 Mpc, the closest file in
  the sample) driving the max SNR up to 31 vs GN's 19. Only 1/81 files exceed GN's max.

### 2.4 CNN performance from `test_scores.csv` in each results folder
| Result set | n (test) | Accuracy | TPR | FPR |
|---|---|---|---|---|
| `result_old_dataset` (GN) | 2574 | 63.5% | 55.9% | 28.0% |
| `results_15k_fainter` | 3000 | 98.9% | 99.8% | 2.0% |

For `results_15k_more_fainter`, injection `optimal_snr` in the test set: min 0.339, p25 0.524,
median 0.609, max 6.993, mean 0.716. The 10 lowest-SNR injections (SNR 0.339–0.377) are classified

For the population the user describes in this message (100,000–200,000 Mpc, optimal SNR ~1e-5),
the same CNN reportedly performs comparably well — this is the population that rules out any
legitimate-physics explanation (see §4).

### 2.5 Code / history review
- `git log -p -- prod/S1/split_dataset.py`: the script never wiped `--out-dir` before writing
  until commit `906ff16` / `f5a165a` (2026-07-24, 18:16–18:18). Before that, re-running the script
  against an existing `--out-dir` (e.g. while iterating on seed/`--test-per-class`) leaves stale
  symlinks from the previous run in `train/`/`val/`, which can silently coexist with a new run's
  `test/` assignment for the same source file — a train/test leak that produces no error and no
  warning.
- `results_15k_fainter`'s artifacts (`Train_val_Accuracy.png`, `training_history.csv`,
  `test_scores.csv`, `paper_net.keras`) are all timestamped 2026-07-24, 15:19–15:58 — **~2.5 hours
  before** the fix landed. Its dataset (`dataset_correct_seed_15k_fainter_inj`) was necessarily
  built with the pre-fix script.
- `git log -p -- CNN/read_data.py`: the train/val-vs-test overlap safety check was rewritten at
  commit `e5c4d1e` (2026-07-24, 10:04) to compare `relpath(train_file, ".../train")` (e.g.
  `"inj/x.png"`) against `basename(test_file)` (e.g. `"x.png"`) — a format mismatch that makes
  genuine duplicates invisible to the check (no set intersection is ever found for a real dup).
  This was not fixed until the same 18:16 commit as `split_dataset.py`. **`results_15k_fainter` was
  generated entirely inside this broken window (10:04–18:16)** — even if train/test leakage
  existed, the intended detector would have silently reported "No images are shared."
- `results_15k_more_fainter`'s artifacts are timestamped 2026-07-26, 10:37–11:55 — two days
  **after** both fixes landed. If its dataset was built fresh with the patched script, this
  specific bug mechanism should not apply — *unless* the output directory was reused from an
  earlier, pre-fix build rather than rebuilt. This can't be confirmed without inspecting the
  cluster filesystem directly (out of scope per current constraints).
- `prod/S1/create_dataset_symlink.py` (a second, separate dataset-splitting script in the repo)
  has the **same class of bug and has never been patched**: `os.makedirs(args.output_dir,
  exist_ok=True)` with no directory reset, and its internal overlap self-check only compares the
  file lists it *just selected*, never checking against files already physically present in the
  output directories from a prior invocation. If this script (rather than `split_dataset.py`) was
  used for any of the `_more_fainter` or other runs, it is unconditionally exposed to the same leak
  today.
- `prod/S1/TT_map_batch_opt.py`: the image-rendering step
  (`save_plot_with_metadata_in_memory`) applies a **fixed** `LogNorm(vmin=0.1, vmax=100)` to every
  image regardless of class or SNR — ruling out a simple "per-image contrast stretch reveals faint
  signals" artifact. The image is a matched-filter SNR map across the **full template bank
  (5446 templates) × time**, not a raw whitened-strain spectrogram — a materially richer input than
  the single-template `optimal_snr` metric used to characterize the population.
- `config_TT_map.ini` (injections) vs `config_TT_map_noise.ini` (noise): identical template bank,
  frequency cutoffs, and template count, but `path_to_time_series` points to two **separate source
  folders** (`preprod/S1/injections_correct_seed_fainter` vs `preprod/S1/noise`). Whether the
  background noise underlying the injections is drawn from the same generation pipeline/seed pool
  as the pure-noise class could not be verified locally — this is the leading non-file-level leak
  hypothesis (see §4).

## 3. What's ruled out

- **Per-image contrast/normalization artifact** — ruled out; normalization is fixed and identical
  across classes (§2.5).
- **"Fainter dataset is just easier"** — ruled out for `fainter` (SNR distribution ~matches GN);
  and for `more-fainter`/the 1e-5-SNR population, "easier" is physically impossible regardless of
  distribution, since the signal is below the noise floor by definition.
- **Template-bank coincidence gain explaining the SNR ~0.3–0.7 results** — plausible on its own
  (bank/time trials can yield a real, if modest, sensitivity gain over a single-template statistic),
  but this explanation **cannot** extend to the 1e-5-SNR population the user just described: the
  maximum plausible bank-trials gain is a small constant factor (~`sqrt(2 ln N)`, roughly 4–5x for
  this bank size), nowhere near enough to make a 1e-5 SNR signal visible. Whatever produces good
  scores on *that* population must be a bug, not statistics.

## 4. Ranked list of possible bug sources

1. **Train/test file-level leakage via stale symlinks** (`split_dataset.py` pre-fix behavior, or
   `create_dataset_symlink.py` at any time — this script has never been patched). Confirmed
   mechanism, confirmed timing overlap for `results_15k_fainter`; timing does not clear
   `results_15k_more_fainter` because dataset-directory reuse cannot be ruled out from here.
2. **Realization-level leakage**: injection background noise and pure-noise-class background drawn
   from different pools/seed streams that share underlying noise-segment recycling. This would not
   show up in any file-hash overlap check (the files are genuinely different) but would let the CNN
   fingerprint "which generator produced this map" — a class of bug entirely consistent with
   *uniformly* excellent performance regardless of injected SNR, including 1e-5.
3. **Class-conditioned asymmetry inside `TT_map_batch_opt.py`** beyond what the shared config
   suggests (different PSD estimation window, segment handling, or floating-point path taken for
   `analysis=='injection'` vs `'noise'`) that isn't visible from the config file alone.
4. **Metadata/filename side-channel**: verify the training data loader never reads PNG `tEXt`
   metadata or filename structure (recall the `noise_` collision-prefix in `split_dataset.py`'s
   test output) as an inadvertent feature.
5. **Checkpoint contamination**: `paper_net.keras` initialized from a checkpoint that had already
   seen overlapping data from a prior (possibly leaky) experiment, rather than trained from scratch.
6. **Batch-composition / BatchNorm leakage**: insufficiently shuffled train/val/test batches letting
   batch-normalization statistics encode class-correlated ordering.
7. **Low-diversity noise pool**: if the "noise" class is generated from a small number of base
   segments with limited variation, the network could learn "matches the canonical noise template or
   not" rather than genuine signal detection — related to but distinct from #2.

## 5. Recommended next steps (for cluster-side verification — not run here)

- Rebuild the `more_fainter`/`fainter` dataset directories from scratch with the current, patched
  `split_dataset.py`, confirm no stale files remain (`ls -la` before/after, check symlink targets),
  and re-run the now-fixed `read_data.py` overlap check, confirming it prints a clean result for
  *these specific* directories.
- Resolve every symlink under `train/`, `val/`, `test/` to its real path and hash-compare file
  content across splits directly — do not trust name-based overlap checks alone.
- Trace whether the noise-class background segments and the injection-class background segments
  share any underlying source files or seed streams (point 2 above). This is the single highest-value
  check given it would explain performance at literally undetectable SNR.
- Run the "zero-amplitude injection" control described in the prior turn: process real noise-only
  strain through the injection code path with signal amplitude forced to zero, and check whether the
  CNN still separates these from real noise-pipeline files at high accuracy. A positive result there
  is conclusive proof of a pipeline/background artifact rather than genuine signal detection.
- Confirm which script (`split_dataset.py` vs `create_dataset_symlink.py`) actually produced each
  dataset directory in use, and patch `create_dataset_symlink.py` with the same output-directory
  reset `split_dataset.py` received, regardless of what the investigation above finds.
